# native-twin — the reference half of the harness

A native scroll view over the same scene `tools/uitrace` replays through
gophics, recording one real gesture into the trace contract. The recording is
the reference; `tools/uitrace/trace/native_test.go` replays its input through
gophics and compares the curves.

## macOS

```
cd tools/native-twin/macos
./build.sh                 # swiftc + Cocoa, no project file
./twin flick.json          # a window opens: flick upward on the trackpad, once
```

The twin records from the first `scrollWheel` event with a gesture phase,
samples the scroll offset every display frame, waits for momentum to end and
the view to go still, writes the file, and quits. One run, one gesture, one
file — a reference recording should be a thing you can point at.

To make it the reference:

```
cp flick.json ../../uitrace/trace/testdata/macos-<machine>-flick.json
go test ./tools/uitrace/trace/ -run Native -v
go run ./tools/uitrace compare flick.json <(go run ./tools/uitrace replay flick.json -out /tmp/r >/dev/null && cat /tmp/r/trace.json)
```

Sign convention is normalized on write: macOS reports `scrollingDeltaY` in
whichever direction the user's natural-scrolling setting implies, and the twin
flips input to the contract (finger up is negative, offset rises) so no
consumer has to guess.

## iOS (Simulator)

```
xcrun simctl boot "iPhone 17 Pro"      # any booted iPhone will do
cd tools/native-twin/ios
./run.sh flick.json                     # builds, installs, launches with console attached
```

Flick upward once in the Simulator window with the mouse; the Simulator turns
a fast drag into a touch flick and `UIScrollView` decelerates on its own
physics. The twin records the pan recognizer's translation deltas — the same
events UIKit derives momentum from — samples `contentOffset` every display
frame, prints the trace to stdout between markers when deceleration ends, and
exits; `run.sh` extracts it. One Swift file, a hand-written Info.plist, and
`simctl` — no Xcode project.

This is the reference that binds: gophics's fling runs on touch platforms, so
`native_test.go` fails the build when a `ios-uikit` recording disagrees beyond
its bands.

## Android (emulator or device)

```
$ANDROID_SDK_ROOT/emulator/emulator -avd <name> -no-window &   # or plug in a device
cd tools/native-twin/android
./run.sh flick.json 100        # build, install, inject a 100ms swipe, pull the trace
```

Four SDK tools and no Gradle: `aapt2` links the manifest, `javac` compiles
against `android.jar`, `d8` dexes, `apksigner` signs with the debug key. The
twin is a `ScrollView` — which flings through `OverScroller` — recording every
MOVE delta in density-independent pixels and `getScrollY()` per Choreographer
frame, written to the app's external files dir where `adb pull` reaches it.

This reference needs nobody: `adb shell input swipe` injects the flick, so the
recording is reproducible to the frame. The injected swipe is a straight line
at constant speed rather than a human finger, which is fine — the finger phase
is replayed identically either way, and only what the platform does after
release is being compared.

## What a recording captures — and does not

On a trackpad, momentum is generated by the OS and delivered as
`momentumPhase` events; the twin's offset series is that curve, sampled per
frame. gophics's desktop shell receives the same OS events, so on a Mac
trackpad the two agree by construction. The comparison matters for gophics's
*own* fling — used on touch platforms where there is no OS momentum — which
imitates this curve. A macOS recording is therefore a reference for what
Apple's decay looks like, and the iOS twin (phase 3) is the reference for the
platform where gophics's fling actually runs.
